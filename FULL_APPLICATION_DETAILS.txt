Authentication flow:
  1. User enters email + password on LoginPage
  2. POST /api/auth/login → returns { access_token, user }
  3. Token saved to localStorage (askora_token)
  4. All backend calls send: Authorization: Bearer <token>
  5. On reload: GET /api/auth/me restores session

Video upload + Q&A flow (frontend side):
  1. User selects video file
  2. Frontend POST /ingest to RAG (NOT backend) with multipart form
  3. Waits for transcription + indexing (can take minutes)
  4. Receives transcript_id, language, num_chunks
  5. User asks question → POST /query with question + transcript_id
  6. Answer displayed on left panel

What is NOT fully wired yet:
  - Chat messages stay in React memory (not saved to backend /api/chats on each message)
  - Recent page only shows current browser session chats
  - Library page uses hardcoded demo data, not live backend videos
  - Video file itself is NOT stored permanently (only processed in RAG temp file)

6. RAG PIPELINE — STEP BY STEP (INGEST + QUERY)
================================================================================

INGEST PIPELINE (video upload → searchable index)
─────────────────────────────────────────────────

Step 1 — AUDIO EXTRACTION
  File    : rag/pipeline/transcription.py
  Tool    : ffmpeg (called internally by whisper.load_audio)
  Input   : Any video/audio file (.mp4, .mkv, .mp3, .wav, etc.)
  Output  : 16 kHz mono PCM audio array
  Note    : ffmpeg MUST be installed: winget install Gyan.FFmpeg

Step 2 — SPEECH TO TEXT (original language)
  File    : rag/pipeline/transcription.py
  Model   : OpenAI Whisper (openai-whisper package)
  Config  : WHISPER_MODEL in rag/.env (default: base)
  Task    : transcribe (detect language + produce original_text)
  Output  : original_text, detected language code (en, hi, ta, es, etc.)

Step 3 — TRANSLATION TO ENGLISH (if not English)
  File    : rag/pipeline/transcription.py
  Task    : translate (Whisper built-in English translation)
  Output  : english_text
  Fallback: If translation fails, english_text = original_text
  Note    : Both original_text AND english_text saved to PostgreSQL

Step 4 — SAVE TRANSCRIPT TO POSTGRESQL
  File    : rag/pipeline/ingestion.py → save_transcript()
  Table   : transcripts (rag/models.py)
  Fields  :
    id, video_id, source_path, title, language, is_english,
    original_text, english_text, duration_seconds, status, indexed,
    created_at, updated_at

Step 5 — TEXT CHUNKING
  File    : rag/pipeline/chunking.py
  Method  : Sentence-aware greedy chunking with character overlap
  Settings:
    CHUNK_SIZE    = 1000 characters
    CHUNK_OVERLAP = 150 characters
  Logic   :
    - Split text on sentence boundaries (. ! ?)
    - Accumulate sentences until chunk_size reached
    - Next chunk starts with last 150 chars of previous chunk (overlap)
    - For scripts without punctuation (Hindi, Tamil, etc.): character-window fallback
  What gets chunked:
    English video     → english/original text only (variant: primary)
    Non-English video → BOTH original language (variant: original)
                        AND english translation (variant: english)

Step 6 — SAVE CHUNK TEXT TO POSTGRESQL
  File    : rag/pipeline/ingestion.py → index_transcript()
  Table   : transcript_chunks
  Fields  : id, transcript_id, chunk_index, content, created_at
  Purpose : Text backup / traceability (separate from vector store)

Step 7 — VECTOR EMBEDDING
  File    : rag/pipeline/embeddings.py
  Library : sentence-transformers
  Model   : paraphrase-multilingual-MiniLM-L12-v2
  Dims    : 384-dimensional vectors
  Runs    : Locally on CPU (no API key, no cloud cost)
  Note    : Multilingual model supports cross-language search
            (e.g. Hindi question can match Hindi or English chunks)

Step 8 — SAVE TO CHROMADB
  File    : rag/pipeline/vectorstore.py
  Location: rag/chroma_db/ (on disk, persistent)
  Collection: transcripts_multilingual
  Metric  : Cosine similarity
  Each stored entry:
    id       = {transcript_id}:{variant}:{chunk_index}
    document = chunk text (the actual words)
    embedding= 384-dim vector (computed by embedding model)
    metadata = { transcript_id, video_id, chunk_index, language, variant }

  After indexing: transcripts.indexed = true in PostgreSQL


QUERY PIPELINE (user question → AI answer)
──────────────────────────────────────────

Step 1 — USER QUESTION RECEIVED
  Frontend sends: POST /query { question, transcript_id }

Step 2 — QUERY EMBEDDING
  File    : rag/pipeline/embeddings.py (via ChromaDB embedding function)
  Same model as chunks: paraphrase-multilingual-MiniLM-L12-v2
  Output  : 384-dim query vector

Step 3 — SIMILARITY SEARCH
  File    : rag/pipeline/vectorstore.py → query()
  Engine  : ChromaDB cosine nearest-neighbor search
  Results : TOP_K = 4 most similar chunks (default)
  Filter  : Scoped to transcript_id (only current video's chunks)
  Output  : List of { text, metadata, distance }
            Lower distance = more relevant

Step 4 — BUILD LLM PROMPT
  File    : rag/pipeline/rag_chain.py
  System  : "Answer ONLY from provided transcript excerpts..."
           "Answer in the SAME language as the user's question."
  Context : Top-K chunk texts combined as [Excerpt 1], [Excerpt 2], ...
  User    : Question + instruction to use context only

Step 5 — LLM ANSWER GENERATION
  Provider: Groq (cloud API)
  Model   : llama-3.3-70b-versatile
  Key     : GROQ_API_KEY in rag/.env
  Temp    : 0.2 (focused, factual)
  Output  : Natural language answer grounded in retrieved chunks

Step 6 — RETURN TO FRONTEND
  Response: { answer, sources[] }
  UI      : Answer on left panel, question on right panel

8. VECTOR DATABASE (CHROMADB) — FULL DETAILS
================================================================================

What is ChromaDB?
  An open-source embedded vector database. Stores text + embeddings on disk.
  Used for semantic (meaning-based) search, not exact keyword search.

Location (local)  : rag/chroma_db/
Collection name   : transcripts_multilingual
Embedding function: LocalEmbeddingFunction (sentence-transformers)
Similarity metric : Cosine distance (hnsw:space = cosine)

How a chunk is stored:
  ┌─────────────────────────────────────────────────────────────┐
  │ ID: abc123:original:0                                       │
  │ Document (text): "Python is a programming language..."      │
  │ Vector: [0.12, -0.34, 0.56, ...] (384 numbers)              │
  │ Metadata:                                                   │
  │   transcript_id = abc123                                    │
  │   video_id      = (optional)                                │
  │   chunk_index   = 0                                         │
  │   language      = hi                                        │
  │   variant       = original | english | primary              │
  └─────────────────────────────────────────────────────────────┘

How search works:
  1. User question → embedded to 384-dim vector
  2. ChromaDB finds vectors with smallest cosine distance
  3. Returns matching chunk texts + metadata + distance scores

View / inspect ChromaDB:
  Browser : http://localhost:8100/viewer
  CLI     : python -m rag.inspect_db
  API     : GET /api/chroma/stats, /api/chroma/chunks, /api/chroma/search?q=...

Important notes:
  - Re-upload videos after changing EMBEDDING_MODEL (vectors become incompatible)
  - Collection name changed to transcripts_multilingual for multilingual model

9. CHUNKING — FULL DETAILS
================================================================================

File     : rag/pipeline/chunking.py
Function : chunk_text(text, chunk_size=1000, chunk_overlap=150)

Why chunk at all?
  - LLMs have context limits — cannot send entire 1-hour transcript
  - Embeddings work best on focused passages (~500-1500 chars)
  - Similarity search returns the most relevant small sections

Algorithm:
  1. Strip whitespace from full transcript text
  2. Split into sentences using regex: (?<=[.!?])\s+
  3. If one giant sentence (> chunk_size, no punctuation): split by character windows
  4. Greedily pack sentences into chunks up to CHUNK_SIZE chars
  5. Each new chunk includes CHUNK_OVERLAP chars from end of previous chunk

Example (English, CHUNK_SIZE=1000, OVERLAP=150):
  Full text: 5000 characters → ~6 chunks for a 4-minute lecture

Example (Hindi/Tamil — no Western punctuation):
  Character-window fallback splits long unpunctuated text into fixed windows

What gets chunked for multilingual videos:
  Non-English: original_text chunks (language=hi, variant=original)
               + english_text chunks (language=en, variant=english)
  English    : single set (language=en, variant=primary)

15. COMPLETE END-TO-END FLOW (ONE SEQUENCE)
================================================================================

 1. User opens http://localhost:5173 and logs in
 2. Backend validates credentials → returns JWT → saved in localStorage
 3. User lands on New Chat (UserDashboard)
 4. User clicks Upload Video and selects a file
 5. Frontend POST /ingest → RAG service (multipart upload)
 6. RAG saves file to temp path
 7. ffmpeg extracts audio from video (via Whisper)
 8. Whisper transcribe pass → original_text + language detected
 9. If not English: Whisper translate pass → english_text
10. Both texts saved to PostgreSQL transcripts table
11. Text chunked (original + english for non-English videos)
12. Chunks saved to PostgreSQL transcript_chunks table
13. Each chunk embedded with multilingual MiniLM model (384 dims)
14. Vectors + text saved to ChromaDB collection transcripts_multilingual
15. RAG returns transcript_id to frontend → "Video processed and ready"
16. User types question in any language on right panel
17. Frontend POST /query { question, transcript_id }
18. Question embedded with same multilingual model
19. ChromaDB finds top 4 most similar chunks (cosine distance)
20. Chunk texts sent as context to Groq llama-3.3-70b-versatile
21. LLM returns grounded answer in user's language
22. Answer shown on left panel
